# prompt-canary

Progressive delivery for LLM prompts, built entirely on Cloudflare: an
immutable prompt version history, SLO-gated canary rollouts, and **automatic
rollback driven by live error rates and LLM-judge eval scores** — no human
has to notice a bad prompt and pull the plug.

Built for the [Cloudflare Software Engineer, Infrastructure Operations](https://job-boards.greenhouse.io/cloudflare/jobs/8212060)
optional take-home assignment. Prompt history for this build is in
[`PROMPTS.md`](./PROMPTS.md), as requested by the assignment brief.

## The idea in one sentence

Chat traffic *is* the canary's test traffic: every turn a user sends gets
generated by whichever version is currently receiving that slice of traffic,
scored by a second LLM acting as judge, and fed into a rolling SLO window
that a durable Workflow checks after every rollout phase — if the numbers
are bad, it reverts to the last known-good version by itself.

## Why this instead of a chat bot

The assignment's four required components — an LLM, workflow/coordination,
chat input, and memory/state — are easy to satisfy with a thin wrapper
around a single `env.AI.run()` call. This project uses all four for a
reason that's actually load-bearing: catching an SLO score requires running
the prompt (LLM #1), scoring the response requires a second, independent
LLM role (LLM #2, the judge), gating a multi-phase rollout with bake time
needs durable multi-step execution (Workflows), and arbitrating "which
version is live right now" under concurrent writes needs a single-writer
coordination point (a Durable Object) — not just "state you could put
anywhere."

It's also a genuine rebuild, not a resubmission: I previously built
[promptX](https://github.com/sudhir-sars/promptX), a Convex/Vercel prompt
CMS that stores and serves prompt *text* but never calls an LLM and uses
Cloudflare only as a KV read cache behind the app. For this assignment I
deliberately rebuilt the interesting third of that idea — versioning +
rollout + rollback — natively on Cloudflare's stack, with the LLM
evaluation loop that actually justifies calling it "AI-powered." No code is
shared between the two repos.

## Architecture

```
                     Chat UI (Workers Static Assets)
                                │  every turn
                                ▼
                        Worker (Hono, src/index.ts)
                                │
          ┌─────────────────────┼─────────────────────┐
          │                     │                      │
          ▼                     ▼                      ▼
   generate reply         judge reply            D1 (immutable)
   Llama 3.3 @ Workers AI Llama 3.3 @ Workers AI  prompts · versions
   (src/lib/ai.ts)        (src/lib/ai.ts)         deployments · rollouts
          │                     │                 eval_events
          └──────────┬──────────┘                      ▲
                      ▼                                 │ audit trail,
              PromptDO (Durable Object, per prompt)      │ queryable history
              - live routing config (who gets traffic)   │
              - rolling eval window (last 200 samples)───┘
              - computeSlo(): error rate, p95 latency,
                schema-valid rate, mean judge score
                      │
                      │ SLO breach after a bake window
                      ▼
          RolloutWorkflow (Cloudflare Workflows)
          5% ──bake──► 25% ──bake──► 50% ──bake──► 100%
           │gate         │gate         │gate         │gate
           └── breach at any phase ──► auto-rollback to baseline
```

- **Workers AI (Llama 3.3)** fills two distinct roles: generating the
  candidate's reply, and — as a separate call with a separate contract —
  judging that reply for relevance and instruction-following. Both are one
  model here, but kept as separate functions because a real deployment
  would often want a cheaper/different model for the judge.
- **Durable Objects** hold the one thing that must never race: which
  version(s) are live right now, and the rolling window of samples the gate
  reads. One `PromptDO` instance per prompt.
- **Workflows** own the rollout's multi-step lifecycle — phase progression,
  bake-time sleeps, gate checks, and rollback — durably. If the Worker
  restarts mid-bake, the Workflow resumes at the same phase instead of
  losing the rollout.
- **D1** is the permanent, queryable, append-only history: every version,
  every deployment (including rollbacks), every rollout, and every
  individual eval event ever recorded. Nothing in it is ever mutated in
  place — a "change" is always a new row.
- **Workers Static Assets** serve the single-page chat + dashboard UI from
  the same Worker, so `wrangler deploy` ships the whole thing.

## What the SLO gate checks

After each rollout phase's bake window, `PromptDO.computeSlo()`
(`src/lib/slo.ts`) evaluates the candidate version's samples from that
window against:

| Signal | Default threshold | Source |
|---|---|---|
| Error rate | ≤ 15% | Did the generation call itself fail? |
| Schema-valid rate | ≥ 90% | Did the model obey the `{"reply": string}` output contract? |
| p95 latency | ≤ 8s | Hard signal, independent of judge opinion |
| Mean judge score | ≥ 0.6 | Composite of the judge's relevance (1–5) and instruction-following (1–5) scores |

Any breach at any phase triggers an immediate rollback: traffic reverts to
100% baseline, and the rollout is marked `rolled_back` with the specific
breach recorded. All four phases passing promotes the candidate.

If a phase gets too little traffic to judge fairly (fewer than 5 samples —
realistic at 5% traffic on light chat volume), the gate treats that as an
inconclusive **pass** rather than a failure: rolling back a good prompt for
lack of data would be worse than proceeding on thin evidence and catching a
real problem at the next, larger phase. This is recorded as
`insufficient_samples` in the verdict for visibility.

## Proven live, not just designed

During development I ran an actual rollout against a deliberately verbose
candidate prompt engineered to overrun the token budget. Under concurrent
chat load, it broke the p95 latency SLO at the 25% phase, and the system
rolled back **on its own** — no manual intervention:

```
rolled_back  phase=1  reason="SLO breach at 25% (p95_latency 10310ms), n=6"
```

Routing reverted to 100% baseline, and the rollback was recorded as an
immutable `deployments` row (`reason: 'auto_rollback'`) alongside the phase
history that led to it.

## Design decisions worth calling out

- **Weighted-random traffic split, not sticky-by-session.** promptX (my
  earlier project) used a SHA-256 session bucket so a user always sees the
  same variant. This project re-samples per turn instead, so the canary's
  live traffic share is visible turn-by-turn in the chat UI during a demo.
  Both are legitimate; sticky routing is the better choice for a real user-
  facing product, which is why I'm noting the tradeoff rather than treating
  it as free.
- **Rollback is forward-only.** A rollback never edits or deletes the
  deployment it's reverting — it inserts a new `deployments` row pointing
  back at the restored config. History is never rewritten, which is also
  why `versions` and `eval_events` are append-only tables.
- **Deliberately narrow scope.** No teams, auth, billing, or multi-tenant
  anything — this is a single-operator control plane, matching the size of
  the assignment rather than promptX's full product surface.

## Running it

```bash
npm install
npm run cf-typegen                                        # generates worker-configuration.d.ts (gitignored)
npx wrangler d1 migrations apply prompt-canary --local    # or --remote
npm run dev       # http://localhost:8787
```

`npm test` runs the SLO-gate, traffic-split, and AI-response-parsing unit
tests (pure logic, no live network calls or wall-clock sleeps — a live
rollout takes minutes per phase by design, which is why the gate math is
tested in isolation rather than end-to-end on every CI run).

```bash
npm run typecheck
npm test
npm run deploy     # wrangler deploy
```

No secrets or API keys are required — Workers AI, D1, and the Durable
Object/Workflow bindings are all Cloudflare-native bindings configured in
`wrangler.jsonc`.
